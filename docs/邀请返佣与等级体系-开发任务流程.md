## Phase 1：邀请绑定模块（后端）✅ 2026-09-30 完成

- [x] 1.1 用户邀请码生成（唯一）+ 邀请链接
- [x] 1.2 注册绑定上级（注册接口加可选 invite_code 字段；链接识别前端后续加）
- [x] 1.3 绑定约束校验：自邀、重复绑定、循环关系（服务端强制，递归 CTE 检测循环）
- [x] 1.4 补绑接口：校验本人无上级 + **本人及所有层级下级**均无成功购买记录（不限三代）
  - ⚠️ 核心红线：**每一层级都必须逐个检查**，从第一代一直查到底，任何一代有成功购买记录即拒绝补绑（含第四代及更深）
  - 检查时机：注册时未绑定 → 后续任何时候补绑都触发全层级检查；注册时已绑定 → 关系永久固定，不再检查
  - 已实现：递归 CTE 全层级购买检查（sqlite/postgres 通用），18/18 端到端测试通过（含"第四代购买拦截补绑"用例）
- [x] 1.5 购买与补绑并发互斥（服务层 assert 预留；购买功能 Phase 2 落地时接入同一校验）
- [x] 1.6 三代关系查询服务 — 随返佣模块（Phase 4）一并实现；补绑检查已用全层级递归 CTE
- [x] 1.7 邀请关系数据永久固定，不提供换绑/解绑

新增文件：`models/invite.py`、`models/order.py`(占位，承载成功购买记录)、`services/invite_service.py`、`routers/invite.py`、`app/lib/services/invite_api.dart`、`app/lib/pages/invite_page.dart`

## Phase 2：产品配置与购买（后端）

- [ ] 2.1 后台产品配置模型：基础日收益率、周期、返还方式（每日/7天/30天/到期）、金额范围、VIP 门槛、团队等级门槛
- [ ] 2.2 上架校验：周期与返还间隔匹配、最低≤最高金额、两项门槛可同时/单独/不设
- [ ] 2.3 购买接口：服务端校验上架状态、金额范围、**生效前** VIP+团队等级（两项同时满足）
- [ ] 2.4 订单生效事件落地（依赖 Phase 0.2 结论）
- [ ] 2.5 订单留存：适用 VIP、锁定加成、资格校验依据、规则版本号

## Phase 3：个人 VIP 等级（后端）

- [ ] 3.1 有效持仓合计 → VIP 0–10 定级（阈值表见需求文档第三节）
- [ ] 3.2 订单锁定机制：按生效前等级锁定加成至到期，升降级不改旧订单
- [ ] 3.3 到期/降级即时重算；升级只影响后续新订单

## Phase 4：团队等级与返佣（后端）

- [ ] 4.1 三代内有效成员统计（单成员有效持仓 ≥300U 计 1 人，多笔合并）
- [ ] 4.2 人数+金额同时达标取最高级，不满足即降级
- [ ] 4.3 等级快照机制（依赖 Phase 0.1）：每个应结算时点记录接收人团队等级
- [ ] 4.4 佣金计算：本期截断后收益 × 对应代数比例（0 级仅一代 5%；1 级一/二代；2 级起三代）
- [ ] 4.5 无资格份额不发放、不越级转移；无上级不发放；平台额外支付不扣下级

## Phase 5：结算引擎（后端，核心）

- [ ] 5.1 四套返还节奏的定时结算：每24h / 每7天 / 每30天 / 到期（按订单生效时间，精确到分钟）
- [ ] 5.2 精度规则：收益、佣金各自截断至 2 位小数（不四舍五入），先截收益再算佣金，禁止合并截断
- [ ] 5.3 到期处理顺序：结最后一期收益+佣金 → 返本入本金账户 → 移除持仓 → 重算 VIP/团队等级
- [ ] 5.4 幂等与唯一业务流水：重试/重复回调不重复入账
- [ ] 5.5 部分失败处理（依赖 Phase 0.10）

## Phase 6：资金账户与提现（后端）

- [ ] 6.1 双账户模型：本金账户 / 收益账户（余额 + 处理中金额分列）
- [ ] 6.2 入账分流：充值→本金；产品收益/佣金→收益账户（明细带来源分类+关联订单）
- [ ] 6.3 提现申请：收益账户 ≥50U 且扣 3% 服务费+网络费；本金账户无门槛无服务费只收网络费
- [ ] 6.4 费用报价展示与确认（提交前报价，确认后不得追加扣费）
- [ ] 6.5 资金占用：申请金额转处理中，拒绝/失败释放；到账必须为正数
- [ ] 6.6 多网络地址格式校验；防绕过校验（收益不得转本金再提）
- [ ] 6.7 充值到账判定（依赖 Phase 0.5）
