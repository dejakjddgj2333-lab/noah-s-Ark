### 第四轮新发现问题

#### N5.【高危】资金密码 + TOTP 已实现但未接入任何资金出口

- `hk_users.fund_password_hash / totp_secret / anti_phishing_code` 列、设置/修改/启停接口全部就绪（routers/auth.py L443-570），但**提现、购买、收益转化三个资金出口代码中完全没有引用 fund_password**（源码全文搜索为零）。
- 影响：token 被盗即可直接提现/转化/购买，资金密码形同虚设。此前"提现无地址白名单/二次确认"缺口实质未补。
- 建议：提现与转化强制资金密码（未设置则先引导设置），大额提现在资金密码之上加邮箱验证码；购买可选。

#### N6.【高危】注销账号不检查余额/持仓/提现处理中

- `deactivate_account`（auth_service.py L137-180）软删除并释放用户名/邮箱，**不校验**账户余额、有效持仓、提现处理中金额。有资金的用户注销后记录保留但永远无法再访问，资金永久沉淀；提现 pending 的申请也无人跟进。
- 建议：注销前置拦截——本金/收益余额 >0、有效持仓 >0、存在 pending 提现时拒绝并提示先提现/到期。

#### N7.【中】admin_orders 列表 total 未应用过滤条件

- [admin_orders.py](server/routers/admin_orders.py) `total` 统计全表订单数，不含 username/status 过滤，前端分页总数与列表不一致。

#### N8.【中】seed_roles 不更新已有角色 perms

- `seed_roles` 只在角色不存在时插入：生产库中已存在的 ops/finance 角色不会获得新增的 `page:orders`、`btn:sweep:target`。新功能页面对老角色不可见，需手动在后台改角色权限（或接受只有超管可见）。

#### N9.【低】转化接口无频控

- `/account/convert` 无 rate limit（有 50U 门槛 + 幂等键，资损风险低，但可高频刷库/日志）。

#### N10.【低】购买限流先于幂等检查

- 同键重试也消耗 10 次/分钟配额；弱网反复重试的极端场景可能误伤（影响小）。

## 一、严重问题（资金/规则级，必须修）

### S1. 佣金按"实际结算时刻"取团队等级，与需求确定的"应结算时点"口径不符

- 位置：`server/services/settlement_service.py` `_settle_commissions` (L101-141)
- 现象：结算执行时实时计算接收人团队等级。需求第四节已明确"按本次收益**应结算时点**的团队等级选取比例"，第九节遗留的只是"延迟时如何还原"的实现方式。
- 影响：引擎停机/积压/一轮扫不完（见 S5）时，接收人等级在延迟期间变化就会**多付或少付佣金**；`receiver_team_level` 留痕字段记录的是错误口径的值，事后无法对账。代码 docstring 已自认此偏差。
- 建议：按待拍板清单建议方案，结算流水已存 `due_at`，用 `hk_level_logs`（等级变动日志含依据快照）还原应结算时点的等级。

### S2. 管理员"改绑上级"接口无任何校验，可直接破坏永久绑定

- 位置：`server/routers/admin_users.py` `update_user` (L277-317)
- 现象：管理员填写邀请码直接覆盖用户已有上级：
  1. **无循环检测** — 可制造 A→B→A 循环，循环后双方三代下线统计互相包含，团队金额重复计算，返佣链失真；
  2. **无购买记录检查** — 把已有订单的用户改挂到新上级下，正是文档明文禁止的"通过后补关系将已有订单或其后续收益挂入新的上级链"；
  3. **直接覆盖已绑定上级** — 违反第一节"上下级关系一旦绑定永久固定，不能更换上级"和第八节验收"已绑定用户再次填写→不能替换原上级"。
- 影响：用户侧 `/invite/bind` 的全部约束（自邀/循环/全层级购买检查）在后台通道被整体绕过。
- 建议：与 `bind_inviter` 同套校验（循环 CTE、全层级购买检查）；已有上级的用户禁止通过该接口变更，或仅限超管+强审批并留痕。

### S3. 被封禁用户的 JWT 依然全站可用

- 位置：`server/services/auth_service.py` `get_current_user` (L53-72)；`server/services/admin_service.py` `get_perms` (L21-24)
- 现象：`get_current_user` 不检查 `user.status`，封禁只拦登录，已签发 token（默认 24h 有效）仍可继续**购买、提现、补绑、充值核销**。`get_perms` 对白名单用户名直通 `['*']`，**被冻结的白名单管理员保留全部后台权限**。
- 影响：被冻结用户照常提现离场，冻结形同虚设。
- 建议：`get_current_user` 增加 `status == "active"` 校验（或缩短冻结场景 token 有效期）；`get_perms` 对非 active 用户直接拒绝。

## 二、高严重度（安全/资损风险）

### S4. 提现幂等键跨用户泄露他人提现记录

- 位置：`server/services/withdraw_service.py` `create_request` (L133-142, L207-214)
- 现象：按 `idempotency_key` 查询时**未过滤 user_id**。用户 B 提交用户 A 用过的 key，会直接返回 A 的提现记录（金额、地址、txid 全泄露），且 B 本次提现请求被静默吞掉。
- 建议：两处查询均加 `HkWithdrawal.user_id == user_id` 条件。

### S5. 结算引擎整批单事务，无异常隔离

- 位置：`server/services/settlement_service.py` `settle_due` (L208-226)
- 现象：一轮最多 200 笔订单在**同一个事务**结算、最后一次性 commit：第 50 笔异常 → 前 49 笔全部回滚；一轮只处理 200 笔，积压订单要等下一轮，进一步放大 S1 的时点偏差。
- 建议：每单独立 commit（单单的幂等已具备），异常单跳过并记录。

### S6. 限流 IP 可被伪造头绕过

- 位置：`server/services/rate_limit_service.py` `client_ip` (L18-23)
- 现象：无条件信任 `X-Forwarded-For` 首跳。服务直接暴露或反代未清洗该头时，攻击者轮换 XFF 即可**完全绕过登录防爆破、注册防批量、发码防轰炸**全部限流。
- 建议：仅在确认经过可信反代时启用 XFF（配置开关），否则用 `request.client.host`。

### S7. 资金归集单权限即可卷款 + 充值私钥明文

- 位置：`server/routers/admin_sweep.py`（targets/run）；`server/models/account.py` `HkDepositAddress.private_key`；`server/services/permissions.py` (L29-34)
- 现象：
  1. 归集目标设置与执行归集共用同一权限码 `btn:sweep:run`：拿到这一个按钮权限即可把主钱包改成自己的地址再一键归集全部池内资金，无审批、无双人；
  2. 充值地址私钥明文存库（注释自认 dev-only），keygen/sweep 均直接使用。
- 建议：目标设置与执行拆分权限/加双人审批；私钥改 KMS/硬件钱包托管，至少加密落库。

## 三、中等问题（功能偏差）

### M1. 佣金接口"应结算时点"字段取错值

- 位置：`server/routers/settlements.py` `my_commissions` (L112)
- 现象：`settle_at=stl.created_at`（实际入账时间）却标注为"应结算时点"；模型中 `HkCommissionRecord.due_at` 已正确留存但未使用。违反文档 8.1 字段口径。
- 建议：改用 `comm.due_at`。

### M2. 补单与扫链并发撞唯一约束 → 未捕获 500

- 位置：`server/services/deposit_service.py` `claim_by_txid` (L245-351)；`server/services/deposit_monitor.py` (L106-141)
- 现象：双路插入同 `(network, txid)`，竞态时 `IntegrityError` 未捕获直接 500；用户输入大小写混合的 txid 同样触发（查询未 lower，存储是小写）。
- 建议：查询统一 `txid.lower()`；插入冲突时重查返回已有记录。

### M3. 审核通过可不填打款交易号

- 位置：`server/routers/admin_withdrawals.py` `ApproveIn` (L39-40)
- 现象：`txid` 为 Optional 且不校验非空，提现可在无任何链上凭证下标记"已打款"，与文档"打款结果不明先核查、全程可追溯"相悖。
- 建议：approve 强制要求 txid（或至少 remark 说明）。

### M4. `_credit` 捕获 IntegrityError 后不回滚

- 位置：`server/services/settlement_service.py` `_credit` (L83-86)
- 现象：PG 下事务进入 aborted 状态，同事务后续全部失败——结算入账途中失败可能静默丢单（sqlite 下侥幸通过）。
- 建议：捕获后 `await db.rollback()` 再重查（参照 `create_request` 的写法）。

### M5. 客服异常流程无数据落地

- 位置：全局缺失
- 现象：文档第七节要求"异常记录关联用户/相关订单或资金流水，记录问题、处理进度及结果"。现有实现只有聊天 + 后台人工查询，**无工单/异常记录实体**，转交与结果反馈无系统留痕、无法查询跟进。
- 建议：建异常工单表（关联用户/单据、问题、进度、结果、处理人），与待拍板清单 9.8 权限矩阵一并落地。

### M6. 秒数未归零，与文档"精确到分钟，秒数不计"不符

- 位置：`server/services/order_service.py` `_create_order_locked`（`effective_at=utc_now()`）
- 现象：15:15:30 生效则次日 15:15:30 才满一日；文档示例为 15:15→15:15。已在待拍板清单 ⚠️3 记录，代码侧尚未改。
- 建议：下单时 `effective_at` 向下取整到分钟。

### M7. CORS 永久放行 localhost 正则

- 位置：`server/app.py` (L242-250)
- 现象：`allow_origin_regex` 不区分环境，生产也允许任意 localhost 来源且 `allow_credentials=true`。
