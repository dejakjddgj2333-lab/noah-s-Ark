## 一、需求文档第九节事项（原文 11 项）

### ✅ 1. 延迟结算与历史等级还原 —— 2026-10-05 已拍板并实施
- **文档原文**：团队等级按收益应结算时点取值已确定；延迟执行时如何还原该时点等级、快照缺失如何处理、历史记录保存要求，待明确。
- **拍板结论**：按建议方案实施 —— 佣金结算时按 due_at 查接收人最后一条 ≤ due_at 的 team 等级日志还原等级（`team_service.team_level_at`）；无覆盖日志时回退最早已知/实时计算。等级与结算流水**永久保存**（只增不改）。
- **验证**：test_s1_restore 5/5（含"延迟期间 1 级→0 级，补结算仍按 1 级发 3%"场景）+ 全套回归 90/90。
- **现状**：结算引擎每分钟扫描，佣金按**实际结算时刻**的团队等级取比例。正常情况应结算时点≈实际结算时刻，无差异；只有服务停机/积压导致延迟结算时才有影响。
- **影响**：延迟结算期间接收人团队等级若变化，佣金按哪个时点算。
- **建议方案**：订单生效时把"未来每个应结算时点的接收人团队等级"全量快照不现实（等级动态变）；建议**按应结算时点重算历史等级**——结算流水已存 due_at，可在结算时用 due_at 对应的等级日志（hk_level_logs 已记录每次等级变动及依据快照）还原当时等级。
- **需要你拍板**：是否按此方案做？历史记录保存时长（如永久）？

### ⏸ 2. 同分钟事件与并发顺序
- **文档原文**：单笔到期顺序已确定；同分钟多笔到期和新购的统一排序、是否同一时点快照、并发新订单如何取得生效前等级，待明确。
- **现状**：结算循环内逐笔串行处理（每单独立事务+幂等）；购买与补绑已加进程互斥锁；引擎一次扫描内的多笔订单按 id 顺序。
- **影响**：同一分钟多笔事件交叉时的等级计算口径。
- **建议方案**：维持串行+幂等即可保证不重复不错漏；"同一时点快照"只有在批量操作时才需要定义，当前业务无批量入口。
- **需要你拍板**：是否接受"串行处理即最终口径"，无需额外定义？

### ⚠️ 3. 订单生效与时间标准
- **文档原文**：订单在哪个事件后生效、秒数如何归零、统一时区及 24 小时计算标准，待明确。
- **现状**：✅ 生效事件已拍板（2026-10-02"购买了就成功"=本金扣款成功即生效）；系统全程 UTC；**秒数未归零**（完整时间戳参与计算，如 15:15:30 生效则次日 15:15:30 满一日）。
- **影响**：文档写"精确到分钟，秒数不计"，与现状有秒级偏差。
- **建议方案**：下单时把 effective_at 的秒/微秒归零（向下取整到分钟），即可完全对齐文档，改动小。
- **需要你拍板**：是否按文档归零到分钟？（归零下"每满24小时为一日"的边界与示例 15:15→次日15:15 完全一致）

### ✅ 4. 邀请入口冲突与无效邀请码
- **现状**：已实质解决——APP 深链识别到的邀请码直接自动填入注册页同一输入框，不存在"链接码与手填码两条并存"的冲突场景；手填可改，以用户最终提交为准。无效邀请码：注册时 400"邀请码无效"明确提示；补绑时同样 400。
- **需要你拍板**：无冲突场景是否需要再定义优先级规则？建议关闭。

### ✅ 5. 支持网络与充值到账规则
- **现状**：远端已落四网络（TRC20/ERC20/BEP20/Arbitrum）充值+提现；每网络固定地址。合约地址/确认数/错链处理细则未定义。
- **需要你拍板**：各网络的代币合约地址、确认数（TRC20 现按 12 确认）、最小充值金额、错链错币的处理话术与流程。

### ⏸ 6. 提现费用报价与审核细则
- **文档原文**：各网络费用来源、报价有效期、费用变化处理；3%服务费/网络费/到账金额的计算精度与取整；审核条件、审批权限、审核与到账时限；拒绝/撤销/链上失败/结果不明的费用退回口径。
- **现状**：✅ 已确认部分已做（收益≥50、3%服务费按申请金额、费用从金额内扣、到账必须为正、多网络地址格式校验、提交前报价+确认后不追加）；网络费为**占位固定值**（TRC20=1/ERC20=5/BEP20=0.3/Arbitrum=0.5）；审核为单人操作无审批流。
- **需要你拍板**：①网络费定价与调整频率 ②单笔/单日限额当前默认 10万/20万 USDT 是否合适 ③审核要不要多级审批 ④审核时限承诺（如 24h）⑤"打款结果不明"的处理 SOP。

### ⏸ 7. 账户资金使用与防绕过边界
- **文档原文**：购买产品可用本金账户还是也可用收益账户？混合支付？若允许收益购买，到期返本归属？充值后直接提现的限制？
- **现状**：**当前仅本金账户可购买**（0.4 部分拍板）；无账户互转通道，收益无法绕门槛；充值后直接提现已受单日/单笔限额约束，无其他限制。
- **需要你拍板**：①收益账户是否开放购买（开放则必须定义返本归属，防止收益→购买→返本金绕 50U 门槛和 3% 服务费）②是否需要充值冷静期（如充值后 24h 内不可提现）？

### ⏸ 8. 异常调整权限与业务后果
- **文档原文**：谁能冻结/解冻账户、调整资金或订单，哪些操作须谁审批；撤销/更正/错误入账对持仓、等级、已发收益佣金的影响；调整须记录原因/操作人/时间/前后数据，不得覆盖原流水。
- **现状**：**异常工单系统未建**（见本文档第二节第 1 条）；已有的追溯能力：admin 审计日志（操作人/对象/明细/时间，只增不改）、资金明细只增不改、等级变动日志。
- **需要你拍板**：权限矩阵（建议：资金调整=超管+双人审批；冻结解冻=管理员；只许冲正不许改原流水）。

### ⏸ 9. 后台规则变更的生效范围
- **文档原文**：上架后修改收益率/周期/返还方式/金额范围/等级门槛/返佣规则的生效时间与版本切换方式；下架产品对已有订单的处理。
- **现状**：保守策略——**已上架产品禁止修改**（须先下架），从物理上杜绝"改参数影响存量订单"；订单已存 rule_version='v0.7' 及完整收益参数快照；下架不影响已购订单结算。
- **需要你拍板**：保守策略是否长期沿用？若允许改已上架产品，须定义"修改即时生效/次日生效+新版本号"。

### ⏸ 10. 结算部分失败与恢复
- **文档原文**：收益或部分佣金入账失败时是否阻断返本、移除持仓及等级重算？重试期限和异常状态。
- **现状**：结算与佣金在同一事务内（要么全部成功要么全部回滚），流水唯一约束保证重试不重复入账；无"部分失败"中间状态。
- **需要你拍板**：事务级回滚即"全部阻断+下轮重试"，是否接受此口径？（建议接受，最简单且不漏不重）

### ✅ 11. 成功购买认定与错误记录更正
- **现状**：✅ 已拍板"扣款成功即生效"；无支付/取消订单概念；退款/撤销原则上不清记录（当前无退款通道）。错误记录更正权限并入第 8 条一起定。

## 二、核对中发现的额外待确认项（文档外）

### ⚠️ 1. 异常工单系统缺失（文档第七节）
- **问题**：文档要求"客服登记→转交→后台处理→反馈"且记录关联用户/订单/流水、处理进度与结果。目前只有后台审计日志（被动记录），**没有用户侧异常登记入口和工单流转表**。
- **建议**：建最小工单表（用户 id/类型/关联单据/问题描述/状态/处理人/处理结果）+ admin 工单页。可等第八节第 8 条权限拍板后一起做。

### ⚠️ 2. APP 新增代码未编译验证
- **问题**：本轮新增 app_links 深链识别、邀请页 APP 直开链接、佣金基数/团队等级展示等 Dart 代码，**本机无 Flutter SDK 从未编译**。
- **需要你确认**：在有 SDK 的机器跑 `flutter pub get && flutter run --dart-define=API_BASE=http://localhost:8000` 验证；重点测深链（adb 命令：`adb shell am start -a android.intent.action.VIEW -d "noahsark://invite?invite=FPYCBJUW"`）。

### ⚠️ 3. 补绑/购买互斥锁仅单进程有效
- **问题**：`services/concurrency.py` 的 asyncio.Lock 只覆盖单 uvicorn 进程。多实例/多 worker 部署时失效。
- **建议**：上线若多实例，换 PostgreSQL advisory lock 或 Redis 分布式锁（改动点已隔离在 concurrency.py 一个文件）。

### ⚠️ 4. 生产数据库遗留数据清理（需你授权）
